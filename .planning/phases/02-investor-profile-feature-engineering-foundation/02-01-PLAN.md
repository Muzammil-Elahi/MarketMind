  <action>
    Run `npx supabase migration new extend_profiles_and_create_holdings` to generate a correctly timestamp-prefixed empty migration file (do not hand-pick a timestamp, per Phase 1 Plan 01's precedent).

    Fill the generated file with exactly the following, all in this one migration:

    (1) `ALTER TABLE public.profiles ADD COLUMN` statements for six new columns, all nullable with no NOT NULL and no DEFAULT (Pitfall 2 — handle_new_user()'s trigger only ever inserts user_id/created_at, so any NOT NULL column here breaks every future signup): `risk_tolerance text` with `CHECK (risk_tolerance IN ('Conservative', 'Moderate', 'Aggressive'))` (D-01); `time_horizon text` with `CHECK (time_horizon IN ('&lt;1yr', '1-3yr', '3-5yr', '5-10yr', '10+yr'))` (D-02); `preferred_sectors text[]`; `excluded_sectors text[]`; `preferred_asset_types text[]`; `capital numeric`.

    (2) `CREATE TABLE public.holdings` with columns: `id uuid primary key default gen_random_uuid()`, `user_id uuid not null references auth.users(id) on delete cascade`, `ticker text not null`, `quantity numeric not null`, `cost_basis numeric` (nullable, D-07), `created_at timestamptz not null default now()`. Do not add a uniqueness constraint on `(user_id, ticker)` — multiple rows for the same ticker are a legitimate multiple-purchase-lot pattern (RESEARCH.md Open Question 2).

    (3) `ALTER TABLE public.holdings ENABLE ROW LEVEL SECURITY`, then exactly four policies, each using `(select auth.uid()) = user_id`, named exactly: `"Users can view their own holdings"` (for select), `"Users can insert their own holdings"` (for insert, `with check`), `"Users can update their own holdings"` (for update, both `using` and `with check`), `"Users can delete their own holdings"` (for delete). Unlike profiles, holdings needs explicit INSERT and DELETE policies since there is no auto-provisioning trigger for it.

    (4) `CREATE INDEX holdings_user_id_idx ON public.holdings (user_id)`.

    (5) `GRANT select, insert, update, delete ON public.holdings TO authenticated;` and `GRANT all ON public.holdings TO service_role;` — in this same migration file (RESEARCH.md's Structure Rationale explicitly recommends folding GRANTs into the same migration as table/RLS creation this time, rather than repeating Phase 1's retroactive two-migration fix pattern).

    Do NOT add any new GRANT statement for `public.profiles` — the existing `grant select, update on public.profiles to authenticated` (20260718211140_grant_profiles_privileges.sql) already covers the six new columns, since Postgres GRANTs are table-level, not column-level.
  </action>
