    Implement five functions:

    `fetch_profile(access_token: str, user_id: str) -> dict | None` — scoped client, `.table("profiles").select("risk_tolerance, time_horizon, preferred_sectors, excluded_sectors, preferred_asset_types, capital").eq("user_id", user_id).execute()`; return `result.data[0]` if present else `None`.     `upsert_profile(access_token: str, user_id: str, *, risk_tolerance=None, time_horizon=None, preferred_sectors=None, excluded_sectors=None, preferred_asset_types=None, capital=None) -> None` — build `payload = {"risk_tolerance": risk_tolerance, "time_horizon": time_horizon, "preferred_sectors": preferred_sectors, "excluded_sectors": excluded_sectors, "preferred_asset_types": preferred_asset_types, "capital": capital}` (exactly these six keys, nothing else — named keyword arguments make mass-assignment structurally impossible here) and call `.table("profiles").update(payload).eq("user_id", user_id).execute()`. Use `.update()` only — never `.upsert()` or `.insert()` — because `public.profiles` has no client-facing INSERT policy; an `.upsert()` call would attempt an insert branch and fail even though the target row already exists (Phase 1's `handle_new_user()` trigger guarantees it does).

    `fetch_holdings(access_token: str, user_id: str) -> list[dict]` — scoped client, `.table("holdings").select("id, ticker, quantity, cost_basis").eq("user_id", user_id).order("created_at").execute()`; return `result.data`.

    `upsert_holdings(access_token: str, user_id: str, rows: list[dict]) -> None` — scoped client; first `.table("holdings").delete().eq("user_id", user_id).execute()` (replace-all-on-save semantics, matching RESEARCH.md's recommendation — no uniqueness constraint exists on ticker, so this is safe). Then, if `rows` is non-empty, build the insert payload as a list comprehension that extracts exactly `{"user_id": user_id, "ticker": row["ticker"], "quantity": row["quantity"], "cost_basis": row.get("cost_basis")}` per row — deliberately not forwarding the entire input row dictionary as-is, so a caller-supplied row containing an unexpected extra key (for example a different `user_id` value) can never override the server-supplied ownership value (T-02-04 mass-assignment mitigation; this is a deliberate refinement of RESEARCH.md's illustrative example, which forwarded the whole row). Call `.table("holdings").insert(payloads).execute()`.

    `validate_ticker(ticker: str) -> bool` — import `fetch_ohlcv` from `src.data.prices`. Call `fetch_ohlcv(ticker, period="5d")` inside a `try`/`except Exception` block. On success, return `status == "live" and not df.empty` (or `not df.empty` regardless of `"live"`/`"stale"` status — a stale-but-non-empty cached row for a previously-valid ticker should also count as valid). On any exception (a genuine live-fetch failure with no cached row at all, Pitfall 4), return `True` — fail-open, since a transient network/API failure is not evidence the ticker symbol itself is invalid, and blocking a user's save on infrastructure flakiness would be worse UX than D-08 intends.
