## User Constraints (from CONTEXT.md)

### Locked Decisions

**Scoring model design**
- **D-01:** Composite score = weighted sum of normalized sub-scores: profile-fit score + factor scores (momentum/volatility/quality-style) + collaborative-similarity score. Each sub-score/weight must be independently displayable to satisfy REC-02's visible-breakdown requirement.
- **D-02:** The "collaborative-filtering-style" component is asset-to-asset (or profile-to-asset-archetype) similarity — e.g. cosine similarity over factor vectors — not true user-user CF, since there's no real interaction history yet. This matches `ARCHITECTURE.md`'s `similarity.py` design (profile ↔ asset-archetype collaborative-style scoring).
- **D-03:** Cross-asset-class normalization uses z-score/percentile ranking computed **within each asset class's own universe** before combining into the composite — avoids unfairly comparing raw crypto volatility to gold volatility. Resolves the "cross-asset-class factor-weight normalization" question flagged as unresearched since Phase 2 (Phase 2 CONTEXT D-09).

**Universe & asset selection**
- **D-04:** Recommendable universe is a fixed, curated list per asset class (config/constant, not live-pulled index membership) — e.g. an S&P100-ish stock subset, ~10-20 popular ETFs, top 10-15 crypto by market cap, gold (GC=F/GLD), major forex pairs. Keeps compute/rate-limit cost bounded and predictable on the free tier.
- **D-05:** Shortlist shows top N **per asset class** (e.g. top 3 stocks + top 3 ETFs + top 3 crypto + gold + top forex pairs), not one flat top-10-15 across all classes — guarantees every supported asset class is represented in the ranked list rather than letting scoring dominance from one class crowd out others.

**Explanation generation**
- **D-06:** The required one-sentence reason (REC-03) is generated by a deterministic template driven by whichever sub-factor(s) contributed most to that asset's score (e.g. "Strong momentum and low volatility match your Moderate risk profile."). No LLM call. Must stay directly traceable to the visible sub-factor breakdown from D-01/D-02, not generic per-asset-class boilerplate.

**Search & asset drill-in**
- **D-07:** REC-04 search is direct ticker lookup via the existing `fetch_ohlcv` chokepoint (Phase 1/2 caching infra) — not fuzzy name-to-ticker matching. Works for any valid yfinance symbol, not limited to the curated D-04 universe.
- **D-08:** When a searched asset has insufficient price history to compute features reliably (e.g. new IPO, thin data), still render the historical price chart but show "insufficient data for scoring" instead of a composite score/breakdown — don't reject the search outright, since REC-04 requires viewing any supported asset.

## Summary

This phase is a pure-Python, zero-I/O scoring problem layered on top of already-built infrastructure (`fetch_ohlcv`, `assemble_feature_frame`, Supabase `profiles`). No new external services and, with one exception (`numpy`, already transitively installed via `pandas`), no new dependencies are required. The three techniques CONTEXT.md locks in — weighted-sum multi-factor scoring, cross-sectional (within-asset-class) z-score/percentile normalization, and cosine similarity for the "collaborative-style" sub-score — are all standard, well-documented quant/recsys patterns with clean pandas/numpy idioms; none of them justify pulling in `scikit-learn` at this scale (a few dozen assets, 2-4 factor dimensions — cosine similarity is a two-line `numpy` formula).

The single biggest technical design decision this research resolves is D-03 (cross-asset-class normalization): compute z-scores or percentile ranks for every factor **within each asset class's own universe** (`df.groupby("asset_class")[factor].transform(...)`) before the weighted blend — this is exactly the pandas `groupby().transform()` pattern quant factor-investing pipelines use, and it structurally prevents crypto's much higher raw volatility from swamping gold's or a utility stock's score. The second major finding is that D-02's "collaborative-filtering-style" framing is a **content-based** similarity (asset factor-vector ↔ profile risk-archetype vector via cosine similarity), not true user-user/item-item CF — which means the classic cold-start problem (no interaction data for a new user/item) **structurally does not apply**: there is no user-item interaction matrix in this design at all, so there is nothing to be "cold" about. This confirms the CONTEXT.md framing is sound and removes a class of design risk the planner might otherwise over-engineer against.

**Primary recommendation:** Build `src/recommendation/{universe.py, factor_scoring.py, similarity.py, engine.py}` as pure pandas/numpy functions (no `st.cache_data`, no I/O) that consume `fetch_ohlcv` + `assemble_feature_frame` + the Supabase profile dict, compute three independently-displayable sub-scores per asset (profile-fit, factor, similarity) via `groupby-transform`-based within-class normalization, combine them with a fixed weighted sum, and generate the REC-03 explanation from a small factor→phrase lookup table keyed off whichever sub-score contributed most — all fully unit-testable with synthetic DataFrames and zero network calls.

### Pattern 1: Weighted-sum composite score with independently displayable sub-scores

**What:** Represent each asset's scoring result as a structured object (dict or small dataclass) carrying the composite score AND each named sub-score/weight separately — never collapse to a single float before the UI layer.
**When to use:** Always for this phase — REC-02 explicitly requires a visible breakdown, not an opaque number.
**Example:**
```python
# Source: pandas weighted-sum/composite-score pattern (general quant/MCDA practice)
# https://www.tempo.io/blog/weighted-scoring-model (composite = sum(weight_k * factor_k))
def compute_composite_score(
    profile_fit: float, factor_score: float, similarity_score: float,
    weights: dict[str, float] = {"profile_fit": 0.4, "factor": 0.35, "similarity": 0.25},
) -> dict:
    composite = (
        weights["profile_fit"] * profile_fit
        + weights["factor"] * factor_score
        + weights["similarity"] * similarity_score
    )
    return {
        "composite_score": composite,
        "sub_scores": {
            "profile_fit": profile_fit,
            "factor": factor_score,
            "similarity": similarity_score,
        },
        "weights": weights,
    }
```

### Pattern 2: Cross-sectional (within-asset-class) normalization via `groupby().transform()`

**What:** Every raw factor value (e.g. `volatility_20`) is converted to a z-score or percentile rank **relative only to other assets in the same asset class**, before being blended into the composite. This is the pandas idiom for "compute a value relative to its group without collapsing the DataFrame."
**When to use:** Always, per D-03 — this is the single locked resolution to the cross-asset-class comparability problem (crypto volatility vs gold volatility are not on the same scale).
**Trade-offs:** Z-score assumes roughly-normal within-class factor distributions and is sensitive to outliers (a single meme-coin volatility spike could skew the whole crypto class's z-scores); percentile rank (`rank(pct=True)`) is more robust to outliers and easier to explain to a non-technical user ("this asset is in the top 20% of its class for momentum") but loses magnitude information (a huge momentum lead over #2 looks identical to a 1% lead). **Recommendation: use percentile rank for the values displayed/explained to the user (more interpretable, bounded [0,1], robust to the small-universe/thin-tail risk this app's curated lists create), and z-score only internally for the similarity sub-score's vector construction if magnitude comparability matters there.**
```python
# Source: pandas groupby().transform() idiom
# https://medium.com/@amit25173/understanding-groupby-transform-in-pandas-b59954153907
# https://educative.io/courses/advance-pandas-going-beyond-the-basics/groupby-transform-and-filter
import pandas as pd

# universe_df has one row per asset: columns include "asset_class", "momentum", "volatility_20", ...
universe_df["momentum_pct"] = (
    universe_df.groupby("asset_class")["momentum"].transform(lambda s: s.rank(pct=True))
)
universe_df["volatility_pct"] = (
    universe_df.groupby("asset_class")["volatility_20"].transform(lambda s: s.rank(pct=True))
)
# Invert volatility percentile for a conservative-leaning "quality" reading if needed:
# low-volatility assets should score HIGH on a "stability" factor, not low.
universe_df["stability_pct"] = 1 - universe_df["volatility_pct"]

# Z-score alternative (use if magnitude, not just rank, matters — e.g. for similarity vectors):
universe_df["momentum_z"] = (
    universe_df.groupby("asset_class")["momentum"]
    .transform(lambda s: (s - s.mean()) / s.std())
)
```

### Pattern 3: Cosine similarity for profile-archetype ↔ asset similarity (D-02)

**What:** Represent each risk-tolerance level (Conservative/Moderate/Aggressive — already the exact three values in `profile.py`'s `RISK_TOLERANCE_OPTIONS`) as a fixed target vector over the same normalized factor dimensions used for `factor_scoring.py` (e.g. `[momentum_pct, stability_pct]`). Compute cosine similarity between each asset's own normalized factor vector and the user's risk-archetype target vector.
**When to use:** For the D-02 "collaborative-filtering-style" sub-score — this is content-based similarity (profile-archetype ↔ asset), not user-user CF, matching CONTEXT.md's explicit framing.
**Trade-offs:** Cosine similarity ignores vector magnitude (only angle/direction matters) — this is usually desirable here since factor values are already normalized to comparable [0,1]/percentile scales, so magnitude differences are already handled by Pattern 2's normalization step, and cosine similarity adds robustness to any residual scale differences between factors.
```python
# Source: numpy dot-product/norm cosine similarity formula (standard, e.g.
# https://memgraph.com/blog/cosine-similarity-python-scikit-learn ,
# https://scikit-learn.org/stable/modules/generated/sklearn.metrics.pairwise.cosine_similarity.html
# — formula shown here implemented in pure numpy, no sklearn dependency needed at this scale)
import numpy as np

# Archetype target vectors over [momentum_pct, stability_pct] dimensions.
# [ASSUMED] — exact target values are a v1 design choice, not derived from
# any external source; tune during planning/execution based on how scores
# look against the curated universe.
RISK_ARCHETYPES = {
    "Conservative": np.array([0.3, 0.9]),   # low momentum need, high stability
    "Moderate":     np.array([0.6, 0.6]),   # balanced
    "Aggressive":   np.array([0.9, 0.2]),   # high momentum, low stability tolerance
}

def cosine_similarity(a: np.ndarray, b: np.ndarray) -> float:
    denom = np.linalg.norm(a) * np.linalg.norm(b)
    if denom == 0:
        return 0.0
    return float(np.dot(a, b) / denom)

def similarity_score(asset_vector: np.ndarray, risk_tolerance: str) -> float:
    archetype = RISK_ARCHETYPES[risk_tolerance]
    # Cosine similarity ranges [-1, 1] for arbitrary vectors, but since both
    # inputs here are non-negative (percentile ranks in [0,1]), the result
    # is bounded to [0, 1] — safe to blend directly with other [0,1] sub-scores.
    return cosine_similarity(asset_vector, archetype)
```

### Pattern 4: Rule-based profile-fit sub-score (sector/asset-type/time-horizon)

**What:** A deterministic checklist-style score, separate from the numeric factor/similarity sub-scores, that encodes the profile's categorical preferences: hard-exclude any stock whose sector is in the user's `excluded_sectors`; boost assets in `preferred_sectors`; only include asset classes the user selected in `preferred_asset_types` (or treat as a scoring boost — see Open Questions); optionally weight momentum vs. stability differently by `time_horizon`.
**When to use:** This is D-01's third sub-score ("profile-fit") and is what makes the recommendation actually personalized rather than a generic top-N-by-factor-score list — per `FEATURES.md`'s explicit finding that "profile answers must visibly change output, or users perceive it as decorative."
**Trade-offs:** Hard-excluding by sector is unambiguous for stocks (each curated stock is tagged with one of the ten `SECTORS` values from `profile.py`) but sector doesn't map cleanly onto ETFs/crypto/gold/forex — see Open Questions for how to handle non-equity asset classes' sector-preference interaction.

### Pattern 5: Template-based one-sentence explanation (D-06)

**What:** A small, static Python dict mapping each factor/sub-score name to a short phrase, plus a simple sentence-assembly function that picks the top 1-2 contributing sub-factors (by normalized value, not raw) and joins their phrases with the user's risk-tolerance label.
**When to use:** Always for REC-03 — CONTEXT.md explicitly forbids an LLM call here.
**Trade-offs:** Per the template-NLG research, this approach is "fast, predictable, and easy to maintain" for a narrow domain but "sounds repetitive" if the phrase library is too small — mitigate with a handful of phrase variants per factor, not just one, without needing to reach for a full templating engine.
```python
# Source: template-based NLG pattern, e.g. TalkToModel-style "fill predefined
# textual templates based on [feature] outputs" —
# https://meta-guide.com/natural-language/nlp/nlg/template-based-natural-language
FACTOR_PHRASES = {
    "momentum_high": "strong upward price momentum",
    "momentum_low": "muted recent momentum",
    "stability_high": "low volatility",
    "stability_low": "higher volatility, suited to growth-oriented exposure",
    "profile_fit_sector": "alignment with your preferred sectors",
    "similarity_high": "a strong match to your {risk_tolerance} risk profile",
}

def explain(top_factors: list[str], risk_tolerance: str) -> str:
    phrases = [FACTOR_PHRASES[f].format(risk_tolerance=risk_tolerance.lower())
               for f in top_factors[:2]]
    joined = " and ".join(phrases)
    return f"{joined.capitalize()} match your {risk_tolerance} risk profile."
    # e.g. "Strong upward price momentum and low volatility match your Moderate risk profile."
```
**Traceability requirement (CONTEXT.md specifics):** `top_factors` here MUST be derived from the exact same sub-score values rendered in the REC-02 breakdown (Pattern 1's `sub_scores` dict) — e.g. `sorted(sub_scores.items(), key=lambda kv: kv[1], reverse=True)` — never a separately-computed "most important factor" that could drift out of sync with what's displayed numerically.

### Pattern 6: Search/drill-in reusing the existing `fetch_ohlcv` chokepoint (D-07/D-08)

**What:** REC-04's search is a direct `fetch_ohlcv(ticker)` call — no new data-layer function, no fuzzy matching. On success with enough history, run the same scoring path as the curated-universe assets (single-asset, no top-N filtering needed). On success with too little history, or on any yfinance failure that still returns a usable (even empty) DataFrame, follow D-08: render the price chart if any data exists, and show "insufficient data for scoring" instead of a composite score.
**When to use:** Always for the search/drill-in page.
**Minimum-history threshold:** No fixed number is specified in CONTEXT.md — `assemble_feature_frame`'s `volatility_20`/`sma_20` need at least 20 trading days and `rsi_14` needs 14; a reasonable, testable threshold is **requiring at least 20 non-NaN rows in the assembled feature frame** before considering the asset scorable, since that's the binding constraint (the longest lookback window already used in `technical.py`). Document this as a named constant, not a magic number, so it's easy for the planner/executor to adjust.

### Anti-Patterns to Avoid

- **Computing "most important factor" for the D-06 explanation from a separate code path than the REC-02 breakdown display:** creates a real risk of the sentence contradicting the visible numbers (explicitly called out as a requirement in CONTEXT.md's Specific Ideas) — always derive both from the same `sub_scores` dict.
- **Normalizing factors across the whole universe (all asset classes at once) instead of within-class:** this is the exact mistake D-03 was written to prevent — a `df["volatility"].rank(pct=True)` with no `groupby("asset_class")` would let crypto's naturally higher volatility dominate percentile ranks and crowd out gold/forex assets from ever scoring well on that factor.
- **Reaching for `scikit-learn.metrics.pairwise.cosine_similarity` or a vector-DB library for a few-dozen-item universe:** unjustified dependency weight at this scale (see Alternatives Considered / Don't Hand-Roll).
- **Calling `yf.Ticker(ticker).info` to fetch sector/fundamental data live:** `PITFALLS.md` and this codebase's existing design (`fetch_ohlcv` is the *only* yfinance chokepoint) both argue against this — `.info` is a separate, slower, historically unreliable yfinance endpoint not currently wired into the caching/backoff chokepoint. Sector tags for the curated stock universe should be **hardcoded as static metadata in `universe.py`** (consistent with D-04's "fixed curated universe, not live-pulled" philosophy), not fetched live.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Cosine similarity math | A manual nested-loop dot-product/magnitude calculation | `numpy.dot()` / `numpy.linalg.norm()` (Pattern 3) | Vectorized, correct, and already a project dependency (transitively) — no reason to hand-write loop-based linear algebra |
| Within-group normalization | A manual `for asset_class in classes: subset = df[df.asset_class==...]; ...` loop | `df.groupby("asset_class")[col].transform(...)` (Pattern 2) | `groupby().transform()` is the canonical pandas idiom for this exact "value relative to its group, same-shaped output" operation — a hand-rolled loop is slower, more error-prone, and non-idiomatic for a pandas-based codebase |
| One-sentence templated text generation | A general-purpose templating engine (Jinja2) or hand-rolled string-grammar system | A plain Python dict + f-string join (Pattern 5) | At "pick 1-2 phrases from a lookup table, join, capitalize" scale, a templating engine is pure overhead — no loops/conditionals/includes are needed in the template itself |
| Ticker universe membership tracking | A live scrape of index constituents (S&P 500, top-N crypto by market cap) at runtime | A static Python list/dict in `universe.py` (D-04) | Explicitly locked by D-04 — live index-membership tracking is a materially larger, rate-limit-risky, non-deterministic engineering problem this project's free-tier/reproducibility constraints don't warrant for v1 |

**Key insight:** Every "don't hand-roll" item above is really "don't reach for infrastructure heavier than the problem needs" — this phase's actual algorithmic core (weighted sum, groupby-transform, cosine similarity, template lookup) is intentionally simple and should stay implemented in <10 lines of pandas/numpy per operation, not wrapped in a framework.

## Common Pitfalls

### Pitfall 1: Cross-asset-class normalization computed globally instead of within-class (D-03's core risk)

**What goes wrong:** A factor like `volatility_20` is normalized (`rank(pct=True)` or z-score) across the *entire* universe DataFrame at once, without `groupby("asset_class")`. Crypto's baseline volatility is typically several multiples of gold's or a large-cap stock's, so every crypto asset ends up clustered at one extreme of the percentile distribution and every gold/forex asset at the other — the "stability" sub-factor becomes meaningless for cross-class comparison, and the D-05 top-N-per-class shortlist ends up implicitly biased even though it's grouped by class downstream.
**Why it happens:** It's the more obvious/less code to write `df["x_pct"] = df["x"].rank(pct=True)` without the groupby, and it "looks right" until you inspect actual per-class score distributions.
**How to avoid:** Every normalization call in `factor_scoring.py` must include `.groupby("asset_class")` — enforce with a unit test asserting that, for a synthetic universe with one artificially high-volatility "crypto" row and one low-volatility "gold" row, the gold row's stability percentile is NOT affected by the crypto row's presence (i.e., changing the crypto row's raw value must not change the gold row's computed percentile).
**Warning signs:** All crypto assets score near-identically low (or high) on a normalized factor regardless of their actual relative differences within crypto; gold/forex assets never appear in the top-N shortlist despite D-05's guarantee they should be represented.

### Pitfall 2: `rank(pct=True)` on a single-row group

**What goes wrong:** If any asset class's curated universe accidentally has only one member (e.g. Gold, per D-04's example of just `GC=F`/`GLD` — a two-item class, or a misconfigured one-item class), `rank(pct=True)` on that group returns `1.0` (or degenerates) for every factor regardless of the actual raw value, and z-score division by a zero/near-zero group standard deviation produces `NaN` or `inf`.
**Why it happens:** Percentile rank and z-score are inherently relative-to-group operations; a group of size 1 has no meaningful "relative to peers" concept, and group size 2 has extremely coarse rank granularity (only two possible percentile values).
**How to avoid:** Ensure the Gold asset class has at least 2-3 members if possible (D-04 already names both `GC=F` and `GLD`, which helps); for any class with `n<3`, guard `factor_scoring.py`'s normalization step against `NaN`/`inf` (e.g. fall back to a fixed default value like `0.5` for that class, and document why) rather than letting a degenerate stat propagate silently into the composite score and explanation template.
**Warning signs:** `NaN` composite scores for Gold or Forex assets; a unit test with a small synthetic per-class universe (size 1-2) exposes this immediately if included.

### Pitfall 3: `.info` calls for stock sector tagging reintroducing yfinance rate-limit risk

**What goes wrong:** Building the curated stock universe's sector tags by calling `yf.Ticker(ticker).info["sector"]` per stock at runtime (rather than hardcoding) reintroduces exactly the per-ticker-loop rate-limit risk `PITFALLS.md` Pitfall 3 already flags for this codebase, and bypasses the `fetch_ohlcv` chokepoint's caching/backoff entirely (`.info` is a separate yfinance code path).
**How to avoid:** Hardcode sector tags as static data in `universe.py` alongside each ticker (Anti-Pattern note above) — this is both faster and consistent with D-04's "fixed curated universe, not live-pulled" design philosophy.
**Warning signs:** New yfinance calls appearing outside `src/data/cache.py`'s chokepoint; `YFRateLimitError` correlated with recommendation-page load rather than price-chart rendering.

### Pitfall 4: Thin-history assets silently producing a misleading score instead of triggering D-08's skip-scoring path

**What goes wrong:** `assemble_feature_frame` returns a DataFrame with mostly-`NaN` `volatility_20`/`sma_20`/`rsi_14` columns for an asset with less than ~20 days of history (e.g. a very recent IPO reached via REC-04 search), but if the scoring code doesn't explicitly check for this, `NaN` values can silently propagate into `groupby().transform()` calls (which by default skip `NaN` when computing group stats, but still assign `NaN` back to that row) and produce a composite score of `NaN` that might render as `0` or a broken UI element instead of the intended "insufficient data for scoring" message.
**How to avoid:** Explicitly check `feature_frame.dropna().shape[0] >= MIN_HISTORY_ROWS` (Pattern 6) before attempting to score an asset at all — treat this as a hard gate before the composite-score computation runs, not something the normalization math is expected to handle gracefully.
**Warning signs:** A searched recently-IPO'd asset shows a composite score of exactly `0` or a broken-looking sub-factor breakdown instead of the D-08-mandated "insufficient data for scoring" message.

## Open Questions

1. **How should `preferred_asset_types` interact with the per-class shortlist (D-05)?**
   - What we know: The profile has a `preferred_asset_types` multi-select (`ASSET_TYPE_OPTIONS = ["Stocks","ETFs","Crypto","Gold","Forex"]`); D-05 says the shortlist shows top-N *per asset class*.
   - What's unclear: If a user selects only "Stocks" and "Crypto," should the shortlist show only those two classes' top-N (skip ETFs/Gold/Forex entirely), or still show one representative from every class but weighted/ranked lower for unselected classes?
   - Recommendation: **Skip asset classes not in `preferred_asset_types` from the ranked shortlist entirely** (treat it as a hard filter, consistent with how `excluded_sectors` is a hard filter for stocks) — this is the simpler, more predictable behavior and matches "profile answers must visibly change output" from `FEATURES.md`. REC-04's search remains the explicit escape hatch for viewing any asset regardless of preferred types (CONTEXT.md D-07 already confirms search works "for any valid yfinance symbol, not limited to the curated D-04 universe").

2. **What exactly is the "quality-style" factor, given the feature layer currently only computes technicals (returns/volatility/SMA/RSI), not fundamentals?**
   - What we know: D-01 lists "factor scores (momentum/volatility/quality-style)" as an example, not a strict enumeration; `assemble_feature_frame` currently outputs exactly 4 columns: `returns`, `volatility_20`, `sma_20`, `rsi_14` — no P/E, ROE, debt/equity, or other fundamentals data source exists in this codebase, and `PITFALLS.md`/this research's Anti-Patterns both argue against adding a live `.info` fundamentals call.
   - What's unclear: Whether the planner should (a) treat "quality-style" as an RSI/trend-stability-derived proxy computed purely from existing technicals (no new data source), or (b) explicitly scope the v1 factor score down to two factors (momentum + stability/volatility) and defer a true fundamentals-based quality factor to a later phase.
   - Recommendation: **Treat "quality-style" as covered by the stability/volatility factor for v1** (RSI can additionally inform a simple "not overbought/oversold" adjustment if desired) — this keeps the phase scoped to data already available via existing chokepoints, avoids introducing a new fundamentals data source mid-phase, and matches the "no Gemini/agent dependency... zero network/LLM calls" purity goal for `recommendation/engine.py`. If a distinct fundamentals-based quality factor is wanted, that should be raised as a separate scoped decision (likely deferred, since it needs a new data source).

3. **Should `time_horizon` affect factor weighting (e.g. longer horizon = more momentum weight, shorter = more stability weight), or only inform the similarity archetype?**
   - What we know: The profile captures `time_horizon` (`<1yr` through `10+yr`) alongside `risk_tolerance`; CONTEXT.md's D-01/D-02 explicitly name `risk_tolerance`-driven similarity but don't mention `time_horizon` in the scoring formula.
   - What's unclear: Whether `time_horizon` should be a second dimension folded into the similarity archetype vectors (e.g. 3 risk levels × 5 horizons = 15 archetype vectors) or left as a pure profile-fit signal (e.g. a minor weighting nudge), or not used in scoring at all this phase (just informational/display).
   - Recommendation: **Keep it simple for v1 — use `time_horizon` only within `profile_fit.py`'s rule-based sub-score (e.g. a small bonus toward higher-momentum assets for longer horizons), not as a second archetype dimension in the similarity cosine calculation.** Expanding the archetype matrix to 15 combinations adds real complexity for a v1 that CONTEXT.md doesn't explicitly request; this can be revisited in a later phase if UAT reveals the recommendation doesn't feel personalized enough by time horizon.
